00Bottom line

Publishing is fixed and verified, so the GUI work is unblocked. The audit found that your complaints were not stylistic — they were accurate descriptions of missing features. Three of them are structural, not cosmetic:

  • There is no log system. No log API exists in the flowkit backend, and the component named LogViewer renders a request table instead of log lines. "Logs are not visible" is literally true — nothing was ever built to show them.
  • The UI lies in specific, findable places. The chat seeds a fabricated assistant message claiming 1,015 reasoning tokens for text no model produced, and invents a reasoning trace when the model returns none. A mock upload's fabricated URL is exposed as a "live URL".
  • Models mismatch because two hand-maintained lists drifted. The dashboard ships one model that does not exist in the reference catalogue, and never queries the live /models endpoint. A hardcoded API key ships in the client bundle.

The new pipeline you asked for — flowkit bridge, watermark scrubber, storyboard — has zero presence in either existing UI. That is why features feel missing: they are.

01Publishing — fixed and verified

YouTube now uploads through the official Data API v3. The previous adapter returned success=True with a hand-written pending_upload URL and no video behind it. That is gone.

New: src/distribution/adapters/youtube_api.py, src/distribution/credentials.py. The adapter refuses to report success without a real video id from the API, enforces title/description/tag limits, and always sets selfDeclaredMadeForKids (without it YouTube rejects the upload).

Fake success removed everywhere

TikTok and Instagram have no supported unapproved posting route, so instead of inventing a success they now fail closed with an explanation. YouTube's old browser-scraper adapter is deprecated and delegates to the API adapter. This is the single most important change for your "empty buttons" complaint: the backend can no longer claim something happened when it did not.

Dry runs are recorded, but never as "published"

An important design decision. Previously a --mock run wrote three publication rows and flipped the episode to published — indistinguishable from a real upload. Now a mock is recorded with status="dry_run" and metadata {"is_mock": true}, and it never transitions the episode. You get the audit trail without the lie.

The reference project already has the correct mechanism — get_all_models() in opencode_endpoint/models.py:151 merges live discovery from the API, local VS Code config, and canonical fallbacks. The dashboard simply does not use it, and keeps its own copy instead.

The fix — one source of truth

  1. Serve the list from the backend. Add a route that calls the reference get_all_models() and returns the live catalogue. The key stays server-side.
  2. Delete the client-side list and the hardcoded key. The frontend fetches models at runtime and never holds a credential.
  3. Validate before sending. If the selected id is not in the live list, refuse the request with a clear message instead of sending it and failing obscurely.
  4. Surface what actually answered. Compare the gateway-reported model against the requested one and show the truth if they differ.
  5. Normalise the endpoint naming so both sides agree on one spelling.
  6. Make discovery failure loud. fetch_models_online() currently returns an empty list on any error, so a stale catalogue looks healthy.

05Target architecture

One control surface instead of three half-finished ones. The flowkit dashboard is already React 19 + shadcn + Radix with routing, i18n, WebSocket and a pipeline tab — it is the right host. The Streamlit app becomes legacy once parity is reached.

The pipeline page becomes the spine. One vertical stage rail, each stage showing its own state and its own log stream:

1 · Scriptdirector output, pacing budget, manifest
2 · Imagesflowkit stills, per-prompt status, retries
3 · Watermarkscrub result, pixels changed, before/after
4 · Assembleclip timings, total duration vs target
5 · Voiceovernarration, audio ducking, mix
6 · Publishdry run vs live, per-platform outcome, real URLs only

What this fixes, directly

  • "Logs not visible" → a real backend log bus plus an xterm.js console per stage, with filtering, search and follow mode.
  • "Empty buttons" → every action returns a typed result, and the UI renders the real outcome. Dry runs are labelled as dry runs.
  • "Features not visible" → the flowkit bridge, scrubber and storyboard each get a surface.
  • "Chat feels templated" → real streaming, real markdown, real reasoning blocks — and no fabricated telemetry.
  • "Models mismatching" → one catalogue, served live from the backend, validated before use.

Where publish data comes from

Publishing is performed by shorts_content_engine, which is headless by design — its own README commits to "zero-GUI batch automation". It has no HTTP API. The dashboard is FlowKit's. So the panel needed a data path, and the choice shaped the rest of the plan.

Decided: the directing engine reports outcomes into FlowKit, and the dashboard reads FlowKit. That keeps one UI, one WebSocket and one log bus rather than a second backend for the browser to talk to. FlowKit's video table already carried youtube_id, privacy and tags, so the schema was already pointing this way.

Three properties are enforced in more than one place, deliberately, because each is a bug that already happened once:

  • A simulated upload is never a publication. Enforced by a Pydantic validator, by the CRUD layer, and by a CHECK constraint on the table — is_mock = 1 forces status = 'dry_run' with no URL and no post id, so the bad state is unrepresentable even if a future caller forgets.
  • A 200 with no platform id is a failure. status = 'published' requires a post_id; without one the API returns 422 rather than recording a phantom post.
  • A mock's fabricated URL never reaches the UI. The reporter drops it at the source, and the table forbids storing it.

Retry is honest about what it can do. The dashboard cannot upload, so pressing Retry records a requested row that the directing engine collects from GET /api/publications/pending. The row stays requested until something actually acts on it — the UI never shows a retry as done merely because it was asked for.
